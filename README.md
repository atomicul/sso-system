# SSO

A single sign-on portal for proprietary apps: an ASP.NET Core minimal API with Identity, and a React single-page app.

## Layout

| Path | What lives there |
|---|---|
| `backend/` | .NET 10 solution: `Sso.Server`, with the endpoints, auth, OpenAPI and EF Core model, and `Sso.Server.Tests`, its integration tests. Its [README](backend/README.md) covers the code patterns |
| `frontend/` | Vite + React SPA: shadcn/ui, TanStack Router, TanStack Query hooks generated by Orval, and i18next translations. Its [README](frontend/README.md) covers the code patterns |
| `deploy/` | Ansible playbooks and the uv scripts that run them, to set the app and its database up on an Ubuntu host |
| `Makefile` | Wires the projects together; none of them refers to another |

Every API route lives under `/api` (`/api/auth/*`, `/api/apps`). The one exception is `GET /health`, which answers
`Healthy` once the API is up and can reach its database, and `503 Unhealthy` otherwise, for probes and `make dev`; it
is not rate limited.

## Requirements

- .NET SDK 10, as pinned in `global.json`
- Node.js 24, as pinned in `frontend/.nvmrc`
- pnpm, as pinned by `packageManager` in `frontend/package.json`
- Docker, for the development database and the backend tests
- uv, which installs the pinned Python and packages of `deploy/`

The .NET SDK is pinned to an exact release because the OpenAPI document, and so the generated frontend client, can
change between .NET patches. To upgrade it, change the version in `global.json` and the `sdk` and `aspnet` image tags in
the `Dockerfile` together, then run `make api` and commit the regenerated client.

## Make targets

| Target | Does |
|---|---|
| `make help` | Lists the targets; also what a bare `make` runs |
| `make install` | Restores the .NET solution and tools (`dotnet-ef`), installs the frontend packages, and syncs `deploy/` with uv |
| `make dev` | Runs the database, the API on `:5080` with `dotnet watch` once the database is up, and the Vite dev server on `:5173` once the API answers `/health`; Vite proxies `/api` to the API |
| `make dev-database` | Runs SQL Server in Docker on `:1433`, keeping its data in the `sso-db-data` volume |
| `make dev-keys` | Generates the development key pairs in `.dev/keys` (`DEV_KEYS`), unless they exist; `make dev` and `make run` sign tokens with `sso.pem` |
| `make reset-dev-database` | Deletes the `sso-db-data` volume, so the next run starts from an empty, freshly migrated database |
| `make migration NAME=AddTags` | Adds an EF Core migration to `backend/Sso.Server/Data/Migrations` after a model change |
| `make api` | Builds the API, copies its OpenAPI document to `frontend/openapi.json` and regenerates the frontend client |
| `make build` | Publishes the API to `out/` with the built SPA in `out/wwwroot`; `VERSION=1.2.3` stamps the API assembly version |
| `make run` | Builds, then serves the API and the SPA together on `:5080` |
| `make check` | Formatting, build, lint, type checks and tests for every project, and fails on model changes without a migration |

Run `make api` after changing an endpoint or contract, and commit the regenerated files.

## Database

The API stores its data in SQL Server through EF Core, reading the `ConnectionStrings:Default` setting. In development,
`make dev` starts SQL Server in Docker and holds the API back until the container's health check can log in; the
Makefile points the API at the container (`DB_CONNECTION`). In the Development environment the API applies pending
migrations from `backend/Sso.Server/Data/Migrations` on startup.

Outside Development the API never migrates its database: deployments apply migrations separately, before starting the
new version, with the Docker image's `migrate` command (see [Docker image](#docker-image)). `make run` runs as
Production, so it expects the development database to be migrated already, e.g. by a previous `make dev`.

## Authentication

ASP.NET Core Identity accepts two schemes:

- **Cookies** for the SPA. It logs in with `POST /api/auth/login?useCookies=true` and gets an HttpOnly cookie, so no
  token is ever visible to JavaScript. `POST /api/auth/logout` clears it.
- **Bearer tokens** for scripts and Swagger UI (`/swagger` in Development).

Only users with a confirmed email can log in. Registering sends a link to the SPA's `/confirm-email` page, which
confirms the address; the login page can send a new link. The API sends emails as [Email](#email) describes. Links use
the API's `SpaUrl` setting as their origin, or the API's own origin when it is unset; `make dev` sets it to the Vite dev
server (`SPA_URL`).

Identity's `IdentityOptions` decide which emails and passwords registration and account changes accept. The API writes
those rules into the `RegisterRequest` and `InfoRequest` schemas of its OpenAPI document, so after changing them,
`make api` updates the SPA's checks. The
SPA explains the rules in its own words, which don't follow them: after changing the password rules, also update
`register.passwordRules` in its catalogs (see the SPA's [Forms](frontend/README.md#forms)).

Signed-in users change their email and password on the SPA's `/account` page, through Identity's
`POST /api/auth/manage/info`:

- A new email takes effect once the user opens the link sent to it, which leads to the same `/confirm-email` page.
  The current email keeps working until then, and `GET /api/auth/manage/pendingEmail` shows the change as waiting
  for as long as its link works: a day, unless the password changes first. Only the latest change can be confirmed:
  asking for another email, or cancelling with `DELETE /api/auth/manage/pendingEmail`, makes the links sent before
  stop working. Asking again for the same email sends a new link, and the earlier ones keep working. An email that
  belongs to another user is refused with a `DuplicateEmail` error.
- A new password needs the current one. The session that changes it stays signed in, while every other session of
  the user ends within 30 minutes, when Identity next checks its security stamp. Confirming a new email ends them
  the same way.

Every page of the SPA except login, registration and email confirmation requires a session.

The app keeps the keys that protect its cookies, bearer tokens and emailed links in the database, so sessions survive
restarts and redeploys and are shared by every instance. Without a certificate, the keys are stored unencrypted, so
anyone who can read the database can forge sessions; restrict access to it accordingly. Setting
`DataProtection:Certificate:Path` to a PFX file, and `DataProtection:Certificate:Password` to its password, encrypts
every new key with that certificate. Keys created before stay readable without it until they expire after 90 days.
Replacing or removing the certificate makes the keys it encrypted unreadable, which logs every user out.

## Client apps

The portal lists the apps configured under `ClientApps` and logs users in to them. Each app has a key of lowercase
letters, digits and dashes, which names it in URLs and in its icon's file name:

```json
"ClientApps": {
  "billing": {
    "Name": "Billing",
    "Endpoint": "https://billing.example.com/sso",
    "PublicKeyPath": "/etc/sso/apps/billing.pub.pem"
  }
}
```

- `GET /api/apps` lists the apps as `{ key, name, iconUrl }`. `iconUrl` is `/api/apps/<key>/icon` when
  `AppIcons:Directory` has a `<key>.jpg`, `<key>.png` or `<key>.webp` file, and `null` otherwise.
- `GET /api/apps/<key>/launch` redirects the user to the app's `Endpoint` with a `token` query parameter, which the
  app's `Sso.Client` library turns into a session.

The token is a JWT signed (RS256) with the SSO's private key at `SigningKey:Path`, then encrypted (RSA-OAEP with
A256CBC-HS512) with the app's public key, so only that app can read it and only the SSO can have written it. It holds
the user's id (`sub`) and `email`, expires after a minute, and its `jti` is the next value of the database's
`LaunchTokenNumbers` sequence. Those numbers only grow, so an app accepts each token once by rejecting any that isn't
newer than the last it accepted for the user. Restoring the database from a backup sets the sequence back, and apps
then reject that user's logins until the numbers catch up.

The API refuses to start without a signing key, with an invalid app, or with two apps that share a public key.
`uv run generate-key-pair` in `deploy/` writes a key pair (see [deploy/README.md](deploy/README.md)).

## Translations

The SPA speaks English and Romanian. It uses the language the user last picked with its switcher, or else the
browser's, and English for any text without a translation. See the SPA's [Translations](frontend/README.md#translations).

The API words its errors in English only, the same for every client, and codes each validation error so clients can
word it in their own language (see the backend's [Validation errors](backend/README.md#validation-errors)). The SPA
shows an error in the user's language when it translates the code, and as the API worded it otherwise.

## Email

The API doesn't send emails yet: it writes every email Identity sends, such as confirmation links and password reset
codes, to its log. Sending them for real means registering another `IEmailSender<IdentityUser>` as the transport in
`Emails.cs`; `SpaLinkEmailSender` keeps pointing the links at the SPA.

## Rate limiting

Every `/api` request is limited per client IP, and requests that send an email (registration, resending the
confirmation link, forgotten passwords and email changes) are held to a stricter limit. Each limit is a fixed window set
in the API's `RateLimits` setting (`RateLimits:Api` and `RateLimits:Email`, each a `PermitLimit` and a `Window`); the
defaults in `appsettings.json` are 100 requests and one email a minute. A rejected request gets a
`429 Too Many Requests` with a `Retry-After` header in seconds.

Behind a reverse proxy, the client IP and scheme come from its `X-Forwarded-For` and `X-Forwarded-Proto` headers,
but only when the proxy is trusted: loopback always is, and `TrustedProxies:Addresses` (IP addresses) and
`TrustedProxies:Networks` (CIDR ranges) add more. Set them before deploying behind one, or every client shares the
proxy's limit.

## HTTPS

The app serves HTTPS itself when Kestrel has an `Https` endpoint, e.g. in `appsettings.Production.json`:

```json
"Kestrel": {
  "Endpoints": {
    "Http": { "Url": "http://*:80" },
    "Https": {
      "Url": "https://*:443",
      "Certificate": { "Path": "/etc/sso/tls/fullchain.pem", "KeyPath": "/etc/sso/tls/privkey.pem" }
    }
  }
}
```

With that endpoint, HTTP requests are redirected to HTTPS, and HTTPS responses carry an HSTS header that tells browsers
to use only HTTPS for the domain for 30 days, so removing the endpoint later breaks the site for returning visitors
until it expires. Without it, nothing changes: behind a reverse proxy that terminates TLS, leave it unset. Kestrel
reads the certificate when the app starts, so restart the app after renewing it.

To get a certificate from Let's Encrypt or another ACME certificate authority without a reverse proxy, point the ACME
client's web root (`certbot --webroot -w`) at a directory and set `AcmeChallenge:WebRoot` to it: the app then serves
the client's challenge files from `/.well-known/acme-challenge/`. Once HTTPS is set up, those requests are redirected
to HTTPS too, which Let's Encrypt follows.

## Docker image

Every semver tag on `main` publishes `ghcr.io/OWNER/REPO`, where `OWNER/REPO` is this repository, tagged with the
version (`1.2.3`) and, for stable releases, `1.2`, `1` and `latest`. GitHub shows this README on the image's package
page. Build the same image locally with `docker build -t sso .`.

The image runs the API and serves the SPA on port `8080` as a non-root user, in the Production environment.
`GET /health` answers `Healthy` once it is up and can reach the database. It runs one of two commands:

| Command | Does |
|---|---|
| _(default)_ | Serves the app: `docker run -p 8080:8080 -e ConnectionStrings__Default=... -e SigningKey__Path=... ghcr.io/OWNER/REPO:1.2.3` |
| `migrate` | Applies pending migrations to the database and exits: `docker run --rm -e ConnectionStrings__Default=... ghcr.io/OWNER/REPO:1.2.3 migrate` |

### Environment variables

Every setting in `appsettings.json` can be set as an environment variable: `__` separates the levels of a key, and
list items take their index as the last level. Both commands read the same settings.

| Variable | Default | Sets |
|---|---|---|
| `ConnectionStrings__Default` | _required_ | The SQL Server connection string, e.g. `Server=db;Database=Sso;User Id=sso;Password=...;TrustServerCertificate=True` |
| `SpaUrl` | the API's own origin | The origin of links in emails |
| `DataProtection__Certificate__Path` | none | A PFX certificate that encrypts the keys protecting sessions, e.g. mounted read-only and readable by the container's non-root user |
| `DataProtection__Certificate__Password` | none | The password of that PFX file |
| `SigningKey__Path` | _required_ | The PEM RSA private key the SSO signs its tokens with (see [Client apps](#client-apps)), e.g. mounted read-only |
| `ClientApps__<key>__Name`, `…__Endpoint`, `…__PublicKeyPath` | none | An app users open from the portal: its name, the URL that receives its tokens, and its PEM public key |
| `AppIcons__Directory` | none | The directory of the apps' icons, `<key>.jpg`, `<key>.png` or `<key>.webp` |
| `TrustedProxies__Addresses__0`, `__1`, ... | none | IP addresses of reverse proxies whose `X-Forwarded-For` and `X-Forwarded-Proto` are trusted |
| `TrustedProxies__Networks__0`, `__1`, ... | none | CIDR ranges of trusted reverse proxies, e.g. `172.16.0.0/12` |
| `Kestrel__Endpoints__Https__Url` | none | An HTTPS address to listen on, e.g. `https://*:8443`, which also redirects HTTP to HTTPS (see [HTTPS](#https)) |
| `Kestrel__Endpoints__Https__Certificate__Path`, `…__KeyPath` | none | The PEM certificate chain and private key of that endpoint |
| `Kestrel__Endpoints__Http__Url` | none | The HTTP address to listen on; Kestrel endpoints replace `ASPNETCORE_HTTP_PORTS`, so set it with an HTTPS endpoint, e.g. `http://*:8080` |
| `HTTPS_PORT` | the HTTPS endpoint's port | The port HTTP is redirected to, when the container's HTTPS port is published on another one |
| `AcmeChallenge__WebRoot` | none | The web root of an ACME client, whose challenge files the app serves (see [HTTPS](#https)) |
| `RateLimits__Api__PermitLimit`, `RateLimits__Api__Window` | `100`, `00:01:00` | Requests per client IP per window, for every `/api` request |
| `RateLimits__Email__PermitLimit`, `RateLimits__Email__Window` | `1`, `00:01:00` | The same, for requests that send an email |
| `ASPNETCORE_HTTP_PORTS` | `8080` | The port the app listens on inside the container |
| `ASPNETCORE_ENVIRONMENT` | `Production` | The environment; keep `Production` in deployments |
| `Logging__LogLevel__Default` | `Information` | The minimum log level |

### Migrations

`migrate` is an [EF Core migration bundle](https://learn.microsoft.com/ef/core/managing-schemas/migrations/applying#bundles)
of the migrations that shipped with the image's version. Run it from the same tag before starting that version. It
creates the database if it is missing, applies only pending migrations, holds a database lock while it does so that
concurrent runs wait for each other, and exits non-zero when it fails. Its output says
`No migrations were applied. The database is already up to date.` when nothing changed.

- `migrate <Migration>` migrates to that migration, reverting the ones after it, e.g. to roll back before deploying an
  older version; `migrate 0` reverts every migration.
- `migrate --connection "<connection string>"` overrides `ConnectionStrings__Default`; prefer the environment variable,
  which keeps the password out of the process list.

## Deploying to a host

`deploy/` sets the app and its database up on a single Ubuntu 24.04 host with Ansible, needing only uv. For each
release, `uv run setup-database user@host v1.2.3` installs SQL Server and migrates it with the release's image, and
`uv run setup-webapp user@host v1.2.3` runs the release as a systemd service. See [deploy/README.md](deploy/README.md).
